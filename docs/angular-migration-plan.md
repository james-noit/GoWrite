# GoWrite → Angular migration plan

Status: **Migration complete and cut over** (2026-09-10) — see §17 for the cutover itself. Every phase in the original roadmap (§4) is done: safety-net tests, the Angular port (editor core, formats, AI layer, remaining UI, `ContextMenu`), and Track B E2E parity verification (§15, 27/27 specs passing identically on both apps before cutover). This file is kept as the historical record of how the migration happened, bug-by-bug and decision-by-decision — not a live status doc anymore.

**A note on file paths below, read this before following any link**: sections written *before* §17 refer to the Angular app under `ng-app/src/...` and the React app under `src/...`, because that's where each one lived *at the time that section was written* — the React app has since been removed and `ng-app/`'s contents moved to the repo root (§17), so today's `src/` is the Angular app both old naming schemes eventually point at. Historical sections are left exactly as originally written rather than rewritten with hindsight; §17 is the only section describing the repo's current, post-cutover layout.

## 0. What GoWrite is today

React 18 + TypeScript + Vite single-page app: a Tiptap/ProseMirror rich-text editor with IndexedDB-backed multi-document storage, five import/export formats (md/txt/html/docx/odt), a multi-provider AI layer (OpenAI/Anthropic/Gemini/Mistral/Cohere/Custom) doing raw SSE streaming for autocomplete/summarize/edit/generate/describe-image/generate-image, and a responsive (mobile+desktop) UI with i18n (es/en) and light/dark theming. No router — one screen. ~2,486 lines of CSS, ~60 source files, 5 test files (all in `src/lib/`, none for components/hooks).

Full inventory (per-file responsibilities, exports, and the current test-coverage gap map) was produced during planning and is summarized in §5 and §7 below; re-derive details from source rather than trusting this doc as files change.

## 1. Recommended approach (flag if you want a different call)

- **New Angular app lives alongside the React app in this repo**, in a new top-level directory `ng-app/`, developed on a long-lived branch (or directly on `main` behind the untouched `src/` — your call at start of Phase 2). The React app keeps shipping from `src/` until Angular reaches parity. Nothing in `src/` is touched during the port except to fix a bug uncovered by the new tests (§6). This avoids a big-bang risk on a working app and lets you run both side by side for manual comparison.
- **Angular version**: latest stable at implementation time (Angular 19/20+ as of this writing) — standalone components (no NgModules), the `@if/@for/@switch` control-flow syntax, and Signals for all state. No NgRx: the app's state graph is shallow (one hook ≈ one piece of state), so a service-per-concern-with-signals model is the direct, idiomatic port of the current hooks and avoids ceremony NgRx would add.
- **Editor**: integrate `@tiptap/core` + `@tiptap/pm` directly (framework-agnostic — this is not React-specific despite the app currently using `@tiptap/react`). A single `EditorService`/directive owns the `Editor` instance lifecycle (`ngAfterViewInit`/`ngOnDestroy`), mirroring [useGoWriteEditor.ts](src/components/Editor/useGoWriteEditor.ts). Most editor extensions ([fontSize.ts](src/components/Editor/fontSize.ts), [formatGroups.ts](src/components/Editor/formatGroups.ts), [tableActions.ts](src/components/Editor/tableActions.ts), [ghostSuggestion.ts](src/components/Editor/ghostSuggestion.ts), [formatPainter.ts](src/components/Editor/formatPainter.ts)) are pure Tiptap/ProseMirror and port with near-zero change. The two React NodeViews ([CodeBlockView.tsx](src/components/Editor/CodeBlockView.tsx), [ImageView.tsx](src/components/Editor/ImageView.tsx)) need Angular-native NodeViews — Tiptap's NodeView API accepts any DOM node, so these become either hand-built DOM (matching the ProseMirror-widget pattern already used in `ghostSuggestion.ts`) or an embedded Angular component created imperatively via `createComponent`/`ApplicationRef` and mounted into the NodeView's `dom`. Prefer hand-built DOM for these two (they're small) to avoid the embedded-component lifecycle complexity.
- **i18n**: keep the current runtime-switchable custom service pattern (port [useI18n.tsx](src/hooks/useI18n.tsx) to an injectable `I18nService` with a `locale` signal), *not* Angular's built-in compile-time i18n — GoWrite needs instant locale toggle without reload, which Angular's `$localize` doesn't support well. [translations.ts](src/lib/i18n/translations.ts) is pure data and ports unchanged.
- **Testing tooling**: Jest (via Angular's native Jest builder / `@angular-builders/jest`) instead of the CLI default Karma/Jasmine, plus **Angular Testing Library** for component tests — closest analogue to React Testing Library, keeps test-writing idiom consistent with the existing Vitest specs so pure-logic tests port with minimal edits. Add **Playwright** for the new end-to-end behavioral suite (§3) — it can run against both the current React dev server and the future Angular one, which is the whole point of writing it before the port starts.
- **Format libraries** (`docx`, `jszip`, `mammoth`) and the **AI layer** (`stream.ts`, `actions.ts`, `providers.ts`, `testConnection.ts`, `imageGen.ts`, `describeImage.ts`) are already 100% framework-agnostic TypeScript with zero React imports. These port by file copy into `ng-app/src/app/core/` with import-path updates only, then get wrapped in thin injectable services for reactivity. This is the majority of the app's hardest logic, and it's also the cheapest to port — prioritize it early to bank confidence.

## 2. The hard parts, ranked

1. **[odt-impl.ts](src/lib/formats/odt-impl.ts) (553 lines)** — hand-rolled ODT XML parser/generator, no library backing it, currently has the thinnest test coverage of any format. Framework-agnostic so it ports by copy, but it's the highest-risk single file for silent regressions. Budget real time for expanding its tests *before* touching it (§3).
2. **[ContextMenu.tsx](src/components/Editor/ContextMenu.tsx) (727 lines)** — a large stage-machine (position → tool → stage → generating → review) mixing raw DOM event listeners, AI orchestration, and format/table actions. Don't port 1:1; decompose into a small `ContextMenuService` (state machine, signals) + several presentational Angular components per tool (summarize/edit/generate/format/image/describe), each independently testable. This is a redesign, not a transliteration — call it out explicitly when you get to Phase 6 so scope doesn't balloon silently.
3. **[Toolbar.tsx](src/components/Editor/Toolbar.tsx) (480 lines)** — responsive FAB/bottom-sheet vs. full bar, a touch-only quick-format popup positioned via `editor.view.coordsAtPos`, and a selection-restore workaround for native color/font pickers stealing ProseMirror focus. The positioning math and focus workaround are the risky bits, not the layout.
4. **[useDocuments.ts](src/hooks/useDocuments.ts)** — has a `ref`-based double-init guard whose whole purpose is surviving React 18 StrictMode's double-invoke of effects. This guard is meaningless in Angular and must not be ported as-is; re-derive the actual invariant it protects (init IndexedDB + run the legacy-localStorage migration exactly once) and implement that directly.
5. **[useViewportInsets.ts](src/hooks/useViewportInsets.ts)** — iOS `visualViewport` keyboard-inset workaround. Small but fiddly; test manually on a real iOS device or simulator since jsdom can't exercise `visualViewport`.
6. **[useAutocomplete.ts](src/hooks/useAutocomplete.ts) + [ghostSuggestion.ts](src/components/Editor/ghostSuggestion.ts)** — debounce/mute/reset state currently lives entirely in refs/closures inside one `useEffect`. Port as an injectable service holding the same state in plain fields (no signals needed here, it's not template-bound) plus the ProseMirror plugin unchanged.

## 3. Testing strategy — the safety net comes first

Only 5 test files exist today, all in `src/lib/`, covering a fraction of even the pure-logic layer; there is **zero** test coverage of any component or hook. Rewriting a UI framework from under an app with this little coverage is how regressions slip through silently. Do not start Phase 2 (Angular scaffolding) until Phase 1 (below) is done.

**Phase 1 has two tracks, run against the *current, unmodified* React app:**

**Track A — expand pure-logic unit tests (Vitest, in `src/`).** These port to the Angular workspace almost verbatim later (same assertions, new import paths), so writing them now is not throwaway effort. Fill the gaps identified during inventory:
- `formatGroups.ts` / `tableActions.ts` — assert `isActive`/`run` against a headless Tiptap editor (extend [testEditor.ts](src/lib/formats/__tests__/testEditor.ts) to include Table/Image/FontSize/Color/Highlight, which it currently lacks — that gap also silently under-tests the existing format round-trip suite).
- `roundtrip.test.ts` gaps — add tables, images, font color/family/size/highlight, text alignment, code blocks, and nested lists for every format (md/txt/html/docx/odt). Add a real **docx import** test (currently export-only "by design," per an inline comment — verify that's still the right call or close the gap; mammoth's browser-only zip reader was cited as the reason, confirm it still applies under jsdom+`fake-indexeddb`-style setup).
- `imageUtils.ts` — `decodeDataUrl`, `extensionForMime`, `scaledSize`.
- `stream.ts` — SSE parsing (`readSse`) and each of the four provider-specific streamers, with mocked `fetch`/`ReadableStream`. This is the single riskiest untested file (hand-rolled SSE parsing per vendor wire format) and should be prioritized.
- `testConnection.ts`, `imageGen.ts`, `describeImage.ts` — model-list parsing tolerance and provider-capability registries.
- `endpoint.ts` — add the missing `customImagesUrl` case.
- `db.ts` — add `getDocument`, confirm the `updatedAt` index is actually used by a query, and document (via a skipped/`.todo` test or comment) that there's no migration path to test yet since `DB_VERSION` has only ever been 1.
- `translations.ts` — a parity test asserting `es` and `en` key sets are identical (this is a real, currently-undetected gap: nothing guarantees the two locale objects stay in sync).
- `formatPainter.ts` — unit test the copy/apply/clear state machine against a headless editor.

**Track B — Playwright end-to-end behavioral specs (new, black-box, framework-agnostic).** These describe *what the app does*, not *how*, so they run unchanged against the React app now and the Angular app later, forming the actual parity contract. Cover, at minimum:
- Create/rename/switch/delete documents (FileMenu + useDocuments CRUD, IndexedDB persistence across reload).
- Type text, apply each formatting group (bold/italic/lists/alignment/font/color/highlight), insert/edit a table, insert/resize/align/caption an image.
- Import and export each of the 5 formats via file picker and via drag-and-drop.
- AI settings: configure a (mocked) provider, connect, see status; run autocomplete accept/reject; run summarize/edit/generate/format/describe-image/generate-image from the context menu; use "undo AI edit."
- Theme toggle, locale toggle, responsive toolbar switch (mobile FAB+sheet vs. desktop full bar — use Playwright's viewport emulation), settings modal tabs, focus-trap/keyboard behavior (Escape closes modals, Tab cycles within them).

Mock AI network calls at the HTTP layer (Playwright route interception) — never hit real provider APIs in CI.

**Track C — bug triage.** Anything Track A/B uncovers that's a genuine behavior bug (not a porting concern) gets fixed in the current React app now, cheaply, while it's still the authoritative implementation — e.g. the `es`/`en` translation-key-parity gap and [FunnyLoader.tsx](src/components/FunnyLoader.tsx)'s hardcoded-Spanish strings (never routed through `useI18n`) are both known, real issues surfaced during inventory and worth fixing in this phase rather than carrying forward.

**During the Angular port itself (Phases 2–6):** write Angular component tests fresh, TDD-style, per component as it's built — don't try to port React Testing Library tests 1:1, since the components are being redesigned (especially `ContextMenu`), not transliterated.

**Phase 7** re-runs the full Track B Playwright suite against the Angular app unmodified as the parity gate.

## 6. Phase 1 results (2026-09-10)

**Track A (pure-logic Vitest coverage):** went from 22 assertions in 5 files to **117 assertions in 13 files**. Closed every gap identified during planning: `testEditor.ts` now mirrors the app's real extension set (Table/Image/FontSize/Color/Highlight/TextAlign/CodeBlock, previously missing); `roundtrip.test.ts` gained coverage for tables, images, font styling, alignment, code blocks and nested lists across md/html/docx/odt; new spec files cover `imageUtils.ts`, `formatGroups.ts`, `tableActions.ts`, `formatPainter.ts`, `stream.ts` (mocked-fetch SSE parsing for all 4 providers + Custom, abort handling, malformed-chunk tolerance, split-chunk parsing), `testConnection.ts`, `imageGen.ts`, `describeImage.ts`, `translations.ts` (es/en key parity), and the remaining `actions.ts` prompt-builders. `db.ts` gained a `getDocument` test. `tsc -b` and `vite build` both stay clean.

**Track B (Playwright E2E):** scaffolded (`playwright.config.ts`, Chromium installed, `npm run test:e2e`, locale pinned to `en-US` for deterministic assertions) with two initial spec files, 10 specs total, all green: [e2e/document-lifecycle.spec.ts](e2e/document-lifecycle.spec.ts) (autosave+reload, rename, create/switch/delete documents) and [e2e/formatting-and-export.spec.ts](e2e/formatting-and-export.spec.ts) (bold/heading toolbar commands, Markdown export download, .txt import, theme toggle+persistence). **Not yet covered** — real follow-up work, not done: AI flows (mocked network — settings connect, autocomplete, summarize/edit/generate/describe-image/generate-image from the context menu), drag-and-drop import, responsive toolbar (mobile FAB/sheet vs. desktop bar), remaining format import/export (html/docx/odt), focus-trap/keyboard behavior, locale toggle.

**Track C — bugs found and fixed in this pass** (all in `src/`, covered by the new tests, verified in a real browser via the dev server in addition to jsdom):
1. **Images silently dropped on re-import** — [image.ts](src/components/Editor/image.ts)'s `Image` extension never set `allowBase64: true`, so `@tiptap/extension-image`'s default (`false`) silently stripped every `data:`-URL image (i.e. every image the app itself ever inserts) whenever a document was re-imported from its own HTML export, or from Markdown/ODT content carrying embedded HTML. Fixed by overriding the option.
2. **ODT export produced invalid XML whenever the document contained an image** — [odt-impl.ts](src/lib/formats/odt-impl.ts)'s `buildContentXml` used the `draw:` and `svg:` namespace prefixes for image frames but never declared them on the root element. This wasn't cosmetic: undeclared namespace prefixes are an XML well-formedness error, so re-importing such a file failed to parse and silently lost the **entire document**, not just the image. Fixed by declaring both namespaces.
3. **ODT import discarded code blocks** — a code block exports as one `Preformatted_Text`-styled paragraph per line (ODT has no dedicated preformatted-block element), but import never grouped those lines back into a single code block, so re-importing turned code into a run of plain paragraphs. Fixed with a `renderBlocks` grouping pass in `odt-impl.ts`.

**Track C — real gaps found but deliberately not fixed** (flagged for a decision, not silently carried forward):
4. **ODT image import is entirely unimplemented**, not just untestable under jsdom as originally assumed — `odt-impl.ts`'s import walker has no case for `<draw:frame>`/`<draw:image>` at all, so images are permanently lost on ODT import even after fix #2 above. Implementing this (decode the embedded `Pictures/*` asset back into a `data:` URL image node) is a real feature addition, out of scope for a test-writing pass — needs its own decision on when to do it (before the Angular port, or during it).
5. **HTML export/import normalizes color representation**: `#ff0000` becomes `rgb(255, 0, 0)` after one round-trip (DOM style-attribute serialization canonicalizes color values on `getHTML()`). Visually identical, but the Settings/Toolbar's `<input type="color">` only accepts `#rrggbb` — a color re-imported from an `.html` export could stop reflecting correctly in that picker even though the text still renders in the right color. Not fixed; worth a small follow-up (normalize back to hex on import, or accept both formats in the picker).
6. **A document ending in a non-text block (e.g. an image) accumulates an extra blank paragraph on every `setContent` pass** — reproducible, minor, root cause not fully chased down (a ProseMirror/Tiptap plugin behavior, not something in `src/`). Low priority; noted for whoever next touches the editor core.
7. **`useDocuments.ts`'s `DEFAULT_FILENAME = 'Documento sin título.md'` is hardcoded Spanish**, bypassing `useI18n` — same class of bug as the `FunnyLoader.tsx` gap below, found via the new Playwright specs (the default document name showed up in Spanish even under a pinned `en-US` locale).
8. `docx` import-test omission is confirmed still correct, not stale: empirically re-verified that `mammoth.convertToHtml` fails under this Vitest/jsdom setup (`Could not find file in options`, from mammoth's browser-only zip reader) even with the browser-field resolution config already in place — the existing "manual verification only" comment in `roundtrip.test.ts` was accurate and needed no change.

**Correction to the original plan:** the speculated `es`/`en` translation-key-parity gap (listed as a "known, real issue" before Phase 1 started) turned out to be **false** — a parity test was added and the two locales' key sets are in fact identical today. Don't carry that claim forward.

- [FunnyLoader.tsx](src/components/FunnyLoader.tsx) phrases are still hardcoded Spanish, bypassing `useI18n` entirely (unchanged from the original plan) — now grouped with finding #7 above as the same class of gap.
- `db.ts` has never exercised a schema migration (`DB_VERSION` has only ever been `1`) — not a bug, but flag it: if Phase 2's port changes the schema at all, this is the first real migration and needs its own test.

## 7. Phase 2 results (2026-09-10)

**Workspace**: scaffolded via `ng new ng-app` at [ng-app/](ng-app) with `--skip-git --routing=false --style=css --ssr=false --test-runner=vitest --zoneless --prefix=gowrite`. ESLint/Prettier "parity" (called for in the original Phase 2 goal) turned out to be moot: the React app has neither an ESLint nor a Prettier config, so there was nothing to match — `ng-app` just keeps the CLI's own scaffolded `.prettierrc`. CI setup was skipped: there's no existing CI in this repo to add a job "alongside," and creating CI infrastructure from scratch wasn't asked for — flagged as an open item below instead of assumed.

**Services ported**, each as an `@Injectable({ providedIn: 'root' })` in `ng-app/src/app/core/`, with signals replacing React state/Context: [storage.service.ts](ng-app/src/app/core/storage.service.ts), [db.service.ts](ng-app/src/app/core/db.service.ts), [i18n/i18n.service.ts](ng-app/src/app/core/i18n/i18n.service.ts) (+ verbatim-copied [translations.ts](ng-app/src/app/core/i18n/translations.ts)), [theme.service.ts](ng-app/src/app/core/theme.service.ts), [media-query.service.ts](ng-app/src/app/core/media-query.service.ts) (+ [breakpoints.ts](ng-app/src/app/core/breakpoints.ts)). `DocumentSnapshot`/`StoredDocument`'s `content` field is deliberately narrowed to `unknown` for now — real typing arrives with Tiptap's `JSONContent` in Phase 3, kept out of Phase 2 on purpose to avoid pulling in editor dependencies early. One React-side hardcoded-Spanish error string in `db.ts` (`No se pudo abrir la base de datos local.`) was initially auto-translated to English during the port by mistake and then reverted — a reminder that "port," not "improve," is the default; language/behavior changes need to go through the same decision process as any other fix (§6/§8), not happen as a drive-by.

32 new tests (Vitest, TestBed where DI/effects are involved — `ThemeService`'s `effect()` needed `TestBed.flushEffects()` to assert synchronously) all pass; `npm test`, `npm run build` both clean. Not yet run through Angular Testing Library or checked against a linter (none configured).

## 8. Phase 3 results (2026-09-10)

**Dependencies**: `@tiptap/core`, `@tiptap/pm`, `@tiptap/starter-kit`, and each individual extension (color/font-family/highlight/image/placeholder/table*/text-align/text-style) plus `tiptap-markdown` installed directly in `ng-app` — no `@tiptap/react`, since Tiptap's core is framework-agnostic and the app no longer renders through React. Hit and fixed a real dependency-resolution bug along the way: pinning `@tiptap/starter-kit` to an exact version while its own transitive extensions floated on caret ranges produced **two nominally-different copies of `@tiptap/core`** in `node_modules` (one nested under `starter-kit`), which TypeScript treats as structurally-incompatible types even though they're nearly identical — surfaced as a wall of `AnyExtension` assignability errors. **Real bug found and fixed via manual browser verification, not caught by unit tests initially**: `EditorService.mount()` passed `onUpdate: options.onUpdate` unconditionally into the `Editor` constructor. When the caller (the bare host component) doesn't supply an `onUpdate` callback, this sets the key to an explicit `undefined` rather than omitting it — and since Tiptap merges the options object with its own internal defaults via a plain spread, an explicit `undefined` **overrides** Tiptap's default no-op handler with `undefined` itself. Every subsequent `editor.on('update', ...)` dispatch then crashed trying to call `undefined.apply(...)`. This didn't surface in jsdom-based Vitest tests at first because none of them happened to call `.mount()` without an `onUpdate` — caught by loading the real dev server in a real browser and driving the editor via a `window.__gwEditor` debug hook (same convention as the React app's `App.tsx`). Fixed by only spreading `onUpdate` into the config when actually provided; a regression test now covers the no-callback path directly through the real `Editor` constructor (not just the extension logic in isolation).

**A real, pre-existing bug found and fixed** — not introduced by the port, but never caught before because `ContextMenu.tsx` had zero test coverage in the original React app (Phase 1's Track A/B explicitly scoped AI-flow/context-menu coverage out to "Phase 6," which itself deferred `ContextMenu` twice more, so it never got written): `acceptDraft()`'s call to record the AI-inserted range for the "Undo last AI generation" affordance computed the end position as `insertRange.from + (sizeAfter - sizeBefore)`. That's correct for a pure insertion (the `generate`/AI-image tools, which insert at a point with nothing deleted), but wrong for a *replacement* (the `edit`/`format` tools, which replace a selection) — the size delta there nets out both the deleted and inserted lengths, so `from + delta` produces an inverted range (`to < from`) whenever the AI's draft is shorter than what it replaced, which is the common case for "Edit with AI" (translating, condensing, correcting). The inverted range made `LastAiEditService.undo()`'s `deleteRange` either silently no-op or throw `RangeError: Position out of range`, reproduced live against a real local AI backend (asked it to replace "mundo" with "Hi" — a 3-character shrink — then clicked "Undo last AI generation"). Fixed by measuring the replacement's end from the *original* range's `to`, not `from`: `insertRange.to + (sizeAfter - sizeBefore)`. Covered by a new regression test exercising exactly that shrink case end-to-end through the real component (not just the isolated service).

## 15. Parity verification results (2026-09-10) — Track B E2E, the table's "Phase 7"

**[playwright.config.ts](playwright.config.ts)** now runs the exact same spec suite against either app: `E2E_TARGET=angular` switches the `baseURL`/`webServer` from Vite (5173) to `ng serve` (4200), nothing else changes. This is the actual parity gate the original plan (§3) called for — a spec that only fails under one target is a real behavioral gap, not a tooling difference.

**The existing 10 Phase-1 specs pass against Angular unmodified**, with one fix needed in [formatting-and-export.spec.ts](e2e/formatting-and-export.spec.ts)'s theme-toggle test: it read `document.documentElement.dataset.theme` immediately after the click, which is correct for React's synchronous state commit but can race Angular's `ThemeService` (a zoneless `effect()` syncing the DOM a tick after the signal updates) — fixed by polling instead of reading once, which is strictly more correct for *both* targets, not an Angular-only workaround. This is the only behavioral difference the whole suite surfaced between the two apps.

**Five new spec files fill the gaps intentionally deferred since Phase 2** ("AI flows, drag-and-drop, responsive toolbar, and html/docx/odt import/export E2E coverage... to be filled in opportunistically during Phase 6" — actually done here, once the real UI existed): [ai-flows.spec.ts](e2e/ai-flows.spec.ts) (settings connect, autocomplete accept-via-Tab, `ContextMenu`'s Summarize/Edit-with-AI end to end, all via Playwright route-mocked `fetch` — never a real provider, per §3's instruction), [format-roundtrip.spec.ts](e2e/format-roundtrip.spec.ts) (export→re-import round-trip for docx/odt/html, the three formats the Phase-1 specs didn't already cover), [drag-and-drop.spec.ts](e2e/drag-and-drop.spec.ts) (simulated via an in-page `DataTransfer` + `evaluateHandle`, since Playwright can't drag a real OS file), [responsive-toolbar.spec.ts](e2e/responsive-toolbar.spec.ts) (viewport emulation for the FAB/sheet vs. inline-bar tier switch), [accessibility.spec.ts](e2e/accessibility.spec.ts) (focus-trap Tab-cycling, Escape/backdrop-click closing modals, Escape closing `ContextMenu`), plus a locale-toggle test added to `formatting-and-export.spec.ts` alongside the existing theme-toggle one. **All 27 specs (10 original + 17 new) pass against both apps.**

**Real bugs in the *tests themselves*, not the apps, found and fixed while writing these** — worth remembering for any future E2E work in this repo:
1. **`download.path()` is a temp file with no extension.** The app picks an import format from the filename's extension, so re-importing a just-downloaded file needs the *real* `download.suggestedFilename()`, not the temp path — passed to `fileChooser.setFiles({name, mimeType, buffer})` instead of a bare path string.
2. **`isVisible()` is a point-in-time snapshot, not an auto-waiting check.** A conditional `if (!(await locator.isVisible())) { ... }` guard around opening `SettingsModal`'s AI-provider accordion raced its own async render (the accordion starts open by default while disconnected) and sometimes toggled it closed right as it was opening — removed the guard entirely once the actual default-open behavior was confirmed, rather than trying to make the timing-sensitive check work.
3. Playwright's `getByRole('button', { name: 'Accept', exact: true })` needs the *exact* accessible name — GoWrite's buttons carry a leading icon glyph (`'✓ Accept'`), so `exact: true` never matches; use `exact: false` (or a regex) for any button whose translation string isn't plain text.
4. A CSS-selector-group locator (`'.a, .b'`) counts as a strict-mode match against *every* element satisfying either half — `.toolbar-ai-card, .toolbar-ai-meta` resolved to 2 elements (a button and its own child span) and failed Playwright's strict mode; target one specific element instead.

**Tests**: 27 E2E specs total now (10 → 27), passing against both `npm run dev` (React, 5173) and `E2E_TARGET=angular` (Angular, 4200). `npm test`/`ng test` (Vitest, 303 tests) and both apps' builds remain clean and untouched by this phase — no source changes in either `src/` or `ng-app/src/`, only `e2e/*`, `playwright.config.ts`.

**One real, pre-existing repo-hygiene bug found and fixed while re-running the React app's own test suite as a sanity check**: root [vitest.config.ts](vitest.config.ts)'s `exclude` list only ever excluded `node_modules/` and `e2e/` — nobody updated it when `ng-app/` was scaffolded in Phase 2, so plain `npm test` at the repo root picked up `ng-app/src/**/*.spec.ts` too and failed all of them with "TestBed not initialized" (root Vitest has no Angular builder wiring TestBed up the way `ng test` does). This had gone unnoticed simply because nobody had run root `npm test` since `ng-app/` started existing. Fixed by adding `'**/ng-app/**'` to the exclude list — React's own suite is back to a clean 117/117.
